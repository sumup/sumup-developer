Online payment webhooks notify your server when a checkout's status changes. Set `return_url` when creating the checkout, then retrieve that checkout from SumUp to verify its final result.

Follow [Confirm a payment and update your order](/online-payments/guides/confirm-payment/) for receiver behavior, verification code, and duplicate-safe order updates.

## Events

This integration sends `CHECKOUT_STATUS_CHANGED` events. Subscribe by setting `return_url` during [checkout creation](/api/checkouts/create/). Cloud API reader payments use a [different event payload](/terminal-payments/cloud-api/payments/#receive-transaction-results).

Ignore event types your application does not recognize and acknowledge them successfully. New event types can be introduced later.

## Handling a Webhook

SumUp sends an HTTPS `POST` to your public `return_url`. Save the verification work durably, then acknowledge the notification promptly. Slow or unsuccessful responses can cause retries.

Your application should return a valid, empty response with any `2xx` status code. Any response other than a `2xx` is treated as erroneous.

<Callout type="note" title="Note">
Retrieve the checkout using server-side credentials and match it to your saved payment attempt before updating the order. Do not fulfill an order from the webhook payload alone.
</Callout>

Here's a sample of the webhook payload:

```json
{
  "event_type": "CHECKOUT_STATUS_CHANGED",
  "id": "id-of-the-changed-checkout"
}
```

## Retries

When an erroneous response is received, a webhook delivery is retried with the following delays:

- 1 minute
- 5 minutes
- 20 minutes
- 2 hours

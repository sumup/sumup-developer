Create an event destination to receive signed HTTP POST notifications when something changes in your SumUp account. Choose the events your application needs, such as `checkouts.paid`, and verify incoming notifications with a [SumUp SDK](/tools/sdks/).

Event destinations are the recommended way to receive events. If you need the older checkout notification flow, see [legacy checkout callbacks](#legacy-checkout-callbacks).

## Create an event destination

Before you start, deploy an endpoint that accepts HTTP POST requests at a publicly accessible HTTPS URL, such as `https://example.com/events`. Localhost, private network addresses, and non-standard ports are not accepted as destination URLs.

1. Open [Event destinations](https://me.sumup.com/settings/event-destinations) in your SumUp account.
2. Select **Create event destination**.
3. Enter a **name** and your endpoint's **URL**. Optionally, add a **description** to explain what the destination is used for.
4. Choose the **events** to subscribe to. For example, select `checkouts.paid` to receive notifications about paid checkouts.
5. Create the destination and obtain its signing secret. Store the secret securely on your server as `SUMUP_EVENT_SECRET`.
6. Configure your receiver to verify signatures with that secret before processing events.

The signing secret belongs to the destination. It is separate from the API key or OAuth access token you use to fetch resources. Event destinations apply to the account's subscribed events; you do not need to set `return_url` on each checkout.

## Events

The event selector lists the available event types. Event families include:

| Resource  | Event types                                                                                         |
| --------- | --------------------------------------------------------------------------------------------------- |
| Checkouts | `checkouts.created`, `checkouts.updated`, `checkouts.paid`, `checkouts.failed`, `checkouts.expired` |
| Sales     | `sales.completed`, `sales.updated`                                                                  |
| Members   | `members.created`, `members.updated`, `members.deleted`                                             |
| Readers   | `readers.created`, `readers.deleted`                                                                |
| Roles     | `roles.created`, `roles.updated`, `roles.deleted`                                                   |

A notification contains a reference to the resource, rather than a full resource snapshot:

```json
{
  "id": "event_01ARZ3NDEKTSV4RRFFQ69G5FAV",
  "type": "checkouts.paid",
  "created_at": "2026-10-15T12:00:00Z",
  "object": {
    "id": "e552de3b-1777-4c91-bdb8-756967678572",
    "type": "checkout",
    "url": "https://api.sumup.com/v0.1/checkouts/e552de3b-1777-4c91-bdb8-756967678572"
  }
}
```

Use the top-level `id` to identify and deduplicate the event. `object.id` identifies the checkout or other resource. Fetch the resource through the SDK when you need its details. The fetched resource represents its current state, which may have changed since the event occurred; deleted resources may no longer be available.

New event types may be added. Acknowledge and ignore types your application does not handle.

## Handling a webhook

1. Read the original request body bytes and the complete `X-SumUp-Webhook-Signature` header.
2. Pass both to your SDK's event handler with the destination's signing secret. Verify before parsing or trusting the payload.
3. Process the event idempotently, or durably enqueue it for processing. Persist processed event IDs so retries cannot repeat business actions.
4. Return an empty `2xx` response, such as `204`, after successful processing or durable acceptance. Return a `5xx` response if processing fails and needs to be retried.

Keep the receiver fast. If you queue events, verify them when they arrive, then process the verified payload from trusted storage. Do not reapply the delivery timestamp check after a long queue delay. Configure request body limits in your HTTP server.

### Verify signatures

The signature header has this format:

```text
X-SumUp-Webhook-Signature: t=<unix timestamp>,v1=<hex HMAC>
```

SumUp signs the exact bytes of `v1:<timestamp>:<raw body>` with HMAC-SHA256 using the destination's signing secret. The SDKs verify the signature and enforce a five-minute window around the signing timestamp. Keep your server clock synchronized. Do not parse and reserialize JSON before verification: even whitespace changes invalidate the signature.

### SDK examples

Install an SDK version that includes event handlers using its [installation guide](/tools/sdks/). Set `SUMUP_EVENT_SECRET` to your destination's signing secret and configure the SDK with an API key or OAuth access token authorized to read the referenced resources.

These examples register a `readers.created` callback, fetch the current reader, and ignore unhandled event types. Subscribe to `readers.created` on your event destination to try them. They show the SDK portion of a receiver: call the function from your HTTP POST route with the unchanged body and signature header. Return `204` only if it succeeds. Reject signature or payload errors with `400`; return `500` for callback or resource-fetch failures. Add persistent deduplication before introducing business side effects.

```go
package receiver

import (
    "context"
    "os"

    "github.com/sumup/sumup-go"
)

func ReceiveEvent(ctx context.Context, body []byte, signature string) error {
    client := sumup.NewClient()
    events, err := client.EventsHandler(
        os.Getenv("SUMUP_EVENT_SECRET"),
        func(context.Context, sumup.EventNotification) error { return nil },
    )
    if err != nil {
        return err
    }
    if err := events.OnReaderCreated(func(ctx context.Context, event *sumup.ReaderCreatedEvent) error {
        reader, err := event.FetchObject(ctx)
        if err != nil {
            return err
        }
        _ = reader // Apply idempotent business updates using event.ID.
        return nil
    }); err != nil {
        return err
    }
    return events.Handle(ctx, body, signature)
}
```

Use `http.MaxBytesReader` before `io.ReadAll` and read the signature with `r.Header.Get(sumup.EventSignatureHeader)`.

To verify your integration, trigger an event you subscribed to, such as pairing a reader for the `readers.created` examples above, or completing a checkout for `checkouts.paid`. Confirm that the matching callback runs and your receiver returns `2xx`. If verification fails, check that the receiver uses the destination's signing secret, reads the original body bytes, and has an accurate server clock.

## Retries

Event deliveries can repeat and can arrive out of order. Use the event `id` for deduplication, including manual redeliveries. Do not deduplicate by the signature or its timestamp: those can change with each attempt.

A `2xx` response acknowledges delivery. Failed requests and other responses are retried with exponential backoff, starting at 5 seconds and capped at 10 minutes, until the attempt limit is reached. A `410 Gone` response deactivates the destination and stops delivery to it. Delivery is not an unlimited guarantee; monitor receiver failures and recover missed updates through the relevant API.

## Legacy checkout callbacks

Use checkout callbacks as a fallback if you cannot use event destinations. This older flow only notifies you about checkout status changes. It uses a different payload and does not use the event destination signature verification shown above.

### Subscribe with `return_url`

To subscribe, specify `return_url` when [creating a checkout](/api/checkouts/create). Set it to the URL of your server's callback endpoint.

### Handle a legacy callback

SumUp sends an HTTP POST request with this payload:

```json
{
  "event_type": "CHECKOUT_STATUS_CHANGED",
  "id": "id-of-the-changed-checkout"
}
```

Before acting on a callback, always [retrieve the checkout](/api/checkouts/get) through the authenticated API to verify its current status. The `id` is the checkout ID, not an event ID. Make your updates idempotent so repeated callbacks do not repeat business actions.

Return a valid, empty `2xx` response promptly. A slow response or a response outside the `2xx` range is treated as a failed notification.

### Legacy retries

Failed legacy callbacks are retried with these delays:

- 1 minute
- 5 minutes
- 20 minutes
- 2 hours

Use separate routes for signed event notifications and legacy callbacks so each route applies the correct payload handling and verification. If both flows are enabled, make business updates idempotent across both notification sources.

## Using paired reader

Cloud API lets you manage transactions and readers connected to your account.

Explore a successful or failed checkout below. The order stays unpaid until your application receives the final transaction result.

## Initiate transaction

This is an asynchronous process; starting the transaction on the device may take some time.

<Tabs syncKey="backend_lang">

      https://api.sumup.com/v0.1/merchants/$SUMUP_MERCHANT_CODE/readers/$READER_ID/checkout \
      -H "Authorization: Bearer $SUMUP_API_KEY" \
      -H 'Content-Type: application/json' \
      -d '{
            "total_amount": {
              "currency": "EUR",
              "minor_unit": 2,
              "value": 1500
            }
          }'

Important notes:

- The target device must be online, otherwise checkout won't be accepted
- After the checkout is accepted, the system has 60 seconds to start the payment on the target device. During this time, any other checkout for the same device will be rejected.
- You need to send the Affiliate Key in the request.

Read the [Create Checkout API endpoint documentation](/api/readers/create-checkout) for details on the API request, examples, and parameter descriptions.

## Receive transaction results

Because the checkout is asynchronous, the API response only confirms that the checkout was accepted—not that the payment succeeded. To receive the final result, pass a `return_url` when creating the checkout. SumUp sends an HTTPS `POST` request to that URL once the transaction reaches a final state.

```bash
curl -X POST \
  https://api.sumup.com/v0.1/merchants/$SUMUP_MERCHANT_CODE/readers/$READER_ID/checkout \
  -H "Authorization: Bearer $SUMUP_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{
        "total_amount": {
          "currency": "EUR",
          "minor_unit": 2,
          "value": 1500
        },
        "return_url": "https://example.com/sumup/webhook"
      }'
```

The `return_url` must use HTTPS and be publicly reachable.

### Webhook payload

The webhook body uses the `solo.transaction.updated` event type:

```json
{
  "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "event_type": "solo.transaction.updated",
  "payload": {
    "client_transaction_id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
    "merchant_code": "M1234567",
    "status": "failed",
    "failure_reason": "Invalid merchant number"
  },
  "timestamp": "2023-10-05T14:48:00Z"
}
```

The `status` field is either `successful` or `failed`. Use `client_transaction_id` to match the webhook against the checkout you started—it holds the same value returned by the Create Checkout response. The `transaction_id` field is deprecated and should not be used in new integrations.

### Failure reason

When `status` is `failed`, the payload may include a `failure_reason` field describing why the transaction did not go through. Use this information to help diagnose failed payments.

Treat the value as free-form text: do not match on exact strings, as new reasons can be introduced at any time.

Do not display `failure_reason` directly to customers. Choose an appropriate customer-facing message instead. For lost-card or stolen-card declines, show a generic payment-declined message.

<Callout type="note" title="Note">
`failure_reason` is only sent for failed transactions. It is omitted from the payload entirely—rather than sent as `null`—for successful transactions, and when no reason is available.
</Callout>

## Terminate transaction

Stops the current transaction on the target device.
This process is asynchronous, and the actual termination may take some time to be performed on the device.

<Tabs syncKey="backend_lang">
  <TabItem label="cURL" icon="seti:powershell">
    ```bash
    curl -X POST \
      https://api.sumup.com/v0.1/merchants/$SUMUP_MERCHANT_CODE/readers/$READER_ID/terminate \
      -H "Authorization: Bearer $SUMUP_API_KEY"
    ```
  </TabItem>
  <TabItem label="JavaScript" icon="seti:javascript">
    ```ts
    await client.readers.terminateCheckout(merchantCode, readerId)
    ```
  </TabItem>
  <TabItem label=".NET" icon="seti:c-sharp">
    ```csharp
    await client.Readers.TerminateCheckoutAsync(merchantCode, readerId);
    ```
  </TabItem>
  <TabItem label="Java" icon="seti:java">
    ```java
    client.readers().createReaderTerminate(merchantCode, readerId, java.util.Map.of());
    ```
  </TabItem>
  <TabItem label="Go" icon="seti:go">
    ```go
    err := client.Readers.TerminateCheckout(ctx, merchantCode, readerID)
    ```
  </TabItem>
  <TabItem label="Python" icon="seti:python">
    ```py
    await client.readers.terminate_checkout(merchant_code, reader_id)
    ```
  </TabItem>
  <TabItem label="Rust" icon="seti:rust">
    ```rust
    client.readers().terminate_checkout(&merchant_code, &reader_id).await?;
    ```
  </TabItem>
</Tabs>

Important notes:

- The target device must be online, otherwise termination won't be accepted.
- This action is only possible if the device is waiting for cardholder action: waiting for card, waiting for PIN, etc.
  There is no confirmation of the termination.
- If a transaction is successfully terminated and `return_url` has been provided on Checkout, the transaction status is sent as `failed` to the provided URL. See [Receive Transaction Results](/terminal-payments/cloud-api/payments/#receive-transaction-results).

Read the [Terminate Checkout API endpoint documentation](/api/readers/terminate-checkout) for details on the API request, examples, and parameter descriptions.

## Verify the result

Match `client_transaction_id` to your stored payment attempt and [retrieve the transaction](/api/transactions/get/) when reconciling the result. Keep the order unpaid until payment is confirmed. See [safe retry guidance](/online-payments/guides/response-handling/) if a request or result is uncertain.

Use a sandbox merchant account to test your in-person payments integration without moving real money. The scenarios below use a SumUp card reader with the [Android SDK](/terminal-payments/sdks/android/), [iOS SDK](/terminal-payments/sdks/ios/), or [Cloud API](/terminal-payments/cloud-api/).

If you use the Cloud API, you can also test without a card reader using [Virtual Solo](/terminal-payments/cloud-api/#solo-virtual-terminal).

For online payments, use the [online payment testing guide](/online-payments/testing/).

## Set up your test

1. [Create a sandbox merchant account](/terminal-payments/quickstart/#sandbox-merchant-account).
2. Authenticate with that sandbox merchant account in your integration. For Cloud API, use credentials for the sandbox merchant and pair the reader with that merchant.
3. Connect a supported reader and make sure it has an internet connection through your phone or its own connection, depending on the integration.
4. Start a payment and tap or insert a supported physical debit or credit card. Follow any instructions on the reader, including PIN entry when requested.

The test amount determines the simulated result once you submit the payment. Card-reading or connection errors can stop the payment before then.

:::caution
The sandbox merchant account determines whether a payment uses real funds. Make sure your app or API request uses the sandbox merchant, even if you have already selected it in [the Dashboard](https://me.sumup.com/dashboard).

For native login in the Android or iOS SDK, we recommend using a managed user account created in your sandbox merchant. Alternatively, set the sandbox merchant account as your [existing user's default merchant](https://me.sumup.com/settings/accounts) before logging in. Follow the [merchant account setup for native SDK login](/terminal-payments/quickstart/#users-with-multiple-merchant-accounts).
:::

### Amount format

Test amounts are listed in [minor units](/tools/glossary/currencies/#minor-units). For example, `4251` means EUR 42.51 or COP 4251 for a reader payment.

## Test successful payments

Start a payment for `1000` minor units (EUR 10.00) and complete the steps on the reader. If your minimum payment amount is higher, choose an allowed amount outside the decline table.

Verify that your integration receives a successful payment result and matches it to the correct order. For Cloud API, wait for the [transaction result](/terminal-payments/cloud-api/#receive-transaction-results): the initial checkout response only confirms that the checkout was accepted.

## Test unsuccessful payments

Choose an exact amount from the table and [format it for your currency](#amount-format).

| Amount in minor units | Simulated reason                    |
| --------------------- | ----------------------------------- |
| `1100`                | Payment declined                    |
| `4201`                | Refer to the card issuer            |
| `4203`                | Invalid merchant                    |
| `4205`                | Payment declined                    |
| `4206`                | Processing error                    |
| `4212`                | Invalid transaction                 |
| `4213`                | Invalid amount                      |
| `4214`                | Invalid card number                 |
| `4241`                | Lost card                           |
| `4243`                | Stolen card                         |
| `4251`                | Insufficient funds                  |
| `4254`                | Expired card                        |
| `4255`                | Incorrect PIN                       |
| `4260`                | Retry PIN entry                     |
| `4261`                | Card usage limit exceeded           |
| `4265`                | Card usage frequency limit exceeded |
| `4275`                | PIN attempt limit exceeded          |
| `4276`                | Additional authentication required  |
| `4278`                | Retry by inserting the card         |
| `4282`                | Invalid card security code          |
| `4291`                | Processing timeout                  |
| `4292`                | Unexpected processing response      |
| `4296`                | System malfunction                  |

Use `4255` minor units to simulate an incorrect PIN while entering the correct PIN. Use `4291` minor units to simulate a processing timeout while the reader stays connected.

For the additional-authentication scenario, the reader may ask you to insert the card or tap it again.

Your SDK, API, or reader may return a more general failure or show different wording. Handle the payment result returned by your integration rather than matching the message displayed on the reader. For Cloud API, see [failure reasons](/terminal-payments/cloud-api/#failure-reason).

:::note
These descriptions identify test scenarios, not messages to display to customers. For lost-card or stolen-card declines, show a generic payment-declined message.
:::

### What to verify

- A declined payment leaves the order unpaid and does not trigger fulfillment.
- Your app shows a clear failure message and lets the customer retry or choose another payment method.
- Each retry uses a new transaction reference, and each result is matched to the correct payment attempt.
- With Cloud API, your integration waits for the final transaction result before updating the order.

## Test reader and connection handling

Also test customer cancellation, a disconnected reader, and loss of connectivity separately. The special amounts above do not reproduce these device or connection conditions.

For store-and-forward payments, follow the separate [offline transaction testing guidance](/terminal-payments/offline-payments/#testing).

Roles control what members can see and do in a merchant account. Use a system role for common jobs, such as managing a shop or handling accounting.

## System roles

SumUp provides four system roles for merchant account members. To assign Manager, Employee, or Accountant through the API, include its ID in the member's `roles` array.

| Role       | ID                | Intended use                                                                                          |
| ---------- | ----------------- | ----------------------------------------------------------------------------------------------------- |
| Admin      | `role_admin`      | Manage the merchant account's settings and preferences. Currently cannot be assigned through the API. |
| Manager    | `role_manager`    | Manage daily business operations, including refunds.                                                  |
| Employee   | `role_employee`   | Perform cashier tasks, such as accepting payments.                                                    |
| Accountant | `role_accountant` | Access reporting and transaction information for accounting.                                          |

SumUp manages the permissions in system roles. [List roles](/api/roles/list/) returns them with `is_predefined: true`.

The account owner has `role_owner` and all Admin permissions. Each merchant account has one owner. This role is not available through the APIs.

## How roles grant access

A **permission** allows an action, such as viewing API keys. A **role** is a set of permissions. SumUp chooses the permissions included in each system role.

A member receives the permissions from all their assigned roles. Removing one role leaves access granted by other roles in place.

### Permissions and OAuth scopes

Permissions control what a user can do in a merchant account. [OAuth scopes](/tools/authorization/oauth/#authorization-scopes) control what your application can do on that user's behalf.

An OAuth request needs both: the user must have the required permission, and the access token must have the required scopes. Requesting a scope does not give the user extra permissions.

Find the required permission for an endpoint in the [API reference](/api/).

## Assign a role to a member

See [Run the examples](/tools/account/#run-the-examples) for shared setup. The user making the request needs `members_update`. For OAuth requests, the token also needs `user.subaccounts` or `members.write`.

Set `SUMUP_ROLE_ID` to the system role to assign, such as `role_manager`. Use [List members](/api/members/list/) to find the member and check their current roles. Set `SUMUP_MEMBER_ID` to their member ID.

**The `roles` array replaces the member's current roles.** Include every role the member should keep. These examples assign only the selected role, removing any other roles from the member:

package main

import (
    "context"
    "fmt"
    "log"
    "os"

    "github.com/sumup/sumup-go"
    sumupclient "github.com/sumup/sumup-go/client"
)

func main() {
    client := sumup.NewClient(sumupclient.WithAPIKey(os.Getenv("SUMUP_ACCESS_TOKEN")))
    member, err := client.Members.Update(
        context.Background(),
        os.Getenv("SUMUP_MERCHANT_CODE"),
        os.Getenv("SUMUP_MEMBER_ID"),
        sumup.MembersUpdateParams{Roles: []string{os.Getenv("SUMUP_ROLE_ID")}},
    )
    if err != nil {
        log.Fatal(err)
    }
    fmt.Printf("%+v\n", member)
}

The API returns HTTP `200` and the updated member. You can also assign the role when [inviting a new member](/api/members/create/). The invited user must accept the invitation to join the account. See [Manage members](/tools/account/members/) for invitation status, managed users, and removing access.

## Verify the member's access

Call [Get a member](/api/members/get/) and check their saved roles. Test an action the role allows and one it should deny using the member's credentials and the required OAuth scopes. A successful request made as the account owner does not verify the member's access.

## Troubleshoot access

If a member cannot perform an action after you assign a role, check:

- The request uses the correct merchant code and the member's credentials.
- The member has the intended role, and the role grants the permission required by the endpoint.
- For OAuth requests, the access token has the endpoint's required scopes.

If the member has more access than expected, check all their assigned roles. Another role may grant the same permission.

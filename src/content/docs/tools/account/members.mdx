Add members to a merchant account so each person can sign in with their own user account. Assign roles to control what they can do. You can also create managed users when the merchant needs to manage the user's login.

See [Run the examples](/tools/account/#run-the-examples) for shared setup.

## Required access

The user making each request needs the corresponding permission. For OAuth requests, the token must also have either of the listed scopes.

| Action                    | User permission  | OAuth scopes                          |
| ------------------------- | ---------------- | ------------------------------------- |
| List members              | `merchant_read`  | `user.subaccounts` or `members.read`  |
| View a member             | `members_view`   | `user.subaccounts` or `members.read`  |
| Invite or create a member | `members_create` | `user.subaccounts` or `members.write` |
| Change a member's roles   | `members_update` | `user.subaccounts` or `members.write` |
| Remove a member           | `members_delete` | `user.subaccounts` or `members.write` |

## Invite a member

1. Choose a [system or custom role](/tools/account/roles/) for the new member.
2. Call [Create a member](/api/members/create/) with the person's email address and the roles to assign.

The following examples invite `teammate@example.com` with the Employee role. Replace the email address before sending a real invitation.

<CodeGroup title="Invite a member">

<CodeGroupItem label="cURL">

```bash
curl --request POST \
  "https://api.sumup.com/v0.1/merchants/${SUMUP_MERCHANT_CODE}/members" \
  --header "Authorization: Bearer ${SUMUP_ACCESS_TOKEN}" \
  --header "Content-Type: application/json" \
  --data '{
    "email": "teammate@example.com",
    "roles": ["role_employee"]
  }'
```

The API returns HTTP `201` and a member object. Save its `id` if you need to update or remove this member later. The person receives an email invitation and must accept it before accessing the account.

Call [Get a member](/api/members/get/) or [List members](/api/members/list/) to check their status. A pending invitation has status `pending`; after acceptance, the member has status `accepted`.

If an invitation expires, the status is `expired`. To replace it, remove its member entry with [Delete a member](/api/members/delete/), then invite the person again. Creating another invitation while an entry for that email already exists is rejected.

If the API returns HTTP `429`, wait until the time indicated by `Retry-After` before retrying.

## Review members and change roles

Use [List members](/api/members/list/) to review who has access to the account. You can filter the results by email prefix, role, or status. The response is paginated: use `limit` and `offset` to retrieve additional pages, with at most 25 members per page.

The following request retrieves the first page of accepted members:

<CodeGroup title="List accepted members">
<CodeGroupItem label="cURL">

```bash
curl --get \
  "https://api.sumup.com/v0.1/merchants/${SUMUP_MERCHANT_CODE}/members" \
  --header "Authorization: Bearer ${SUMUP_ACCESS_TOKEN}" \
  --data-urlencode "status=accepted" \
  --data-urlencode "limit=25" \
  --data-urlencode "offset=0"
```

</CodeGroupItem>
</CodeGroup>

The API returns HTTP `200` with an `items` array and `total_count`. Increase `offset` by the number of items returned to retrieve the next page. Use a member's `id` to update their roles or remove their access.

## Assign a role to a member

The user making the request needs `members_update`. For OAuth requests, the token also needs `user.subaccounts` or `members.write`.

Set `SUMUP_ROLE_ID` to the custom role ID returned by Create a role, or a system role ID such as `role_manager`. Use [List members](/api/members/list/) to find the member and check their current roles. Set `SUMUP_MEMBER_ID` to their member ID.

**The `roles` array replaces the member's current roles.** Include every role the member should keep. These examples assign only the selected role, removing any other roles from the member:

<CodeGroup title="Assign a role to a member">

<CodeGroupItem label="cURL">

```bash
curl --request PUT \
  "https://api.sumup.com/v0.1/merchants/${SUMUP_MERCHANT_CODE}/members/${SUMUP_MEMBER_ID}" \
  --header "Authorization: Bearer ${SUMUP_ACCESS_TOKEN}" \
  --header "Content-Type: application/json" \
  --data "{\"roles\":[\"${SUMUP_ROLE_ID}\"]}"
```

### Verify the member's access

Call [Get a member](/api/members/get/) and check that their roles include `SUMUP_ROLE_ID`. Call [Get a role](/api/roles/get/) to review its permissions.

Make test requests using that member's credentials and the scopes required by each endpoint. Check an action the role allows and one it should deny. For the API key viewer role, listing API keys should succeed, while creating one should be denied unless another role grants that permission. A successful request made as the account owner does not verify the member's access.

## Managed users

An invited member signs in with their own user account. A managed user's login is managed by the merchant instead, and no invitation is sent. Managed users cannot reset their own password; the merchant must change it with [Update a member](/api/members/update/).

To create a managed user, call [Create a member](/api/members/create/) with `is_managed_user: true`, an email address, a password, and the roles to assign. You can also provide a `nickname` for display. The password must contain at least eight characters.

Export `SUMUP_MANAGED_USER_PASSWORD` with the password for the new managed user. The following request creates `cashier@example.com` with the Employee role. Replace the email address before sending the request.

<CodeGroup title="Create a managed user">
<CodeGroupItem label="cURL">

```bash
curl --request POST \
  "https://api.sumup.com/v0.1/merchants/${SUMUP_MERCHANT_CODE}/members" \
  --header "Authorization: Bearer ${SUMUP_ACCESS_TOKEN}" \
  --json "$(jq -n '{
    email: "cashier@example.com",
    is_managed_user: true,
    password: env.SUMUP_MANAGED_USER_PASSWORD,
    nickname: "Cashier",
    roles: ["role_employee"]
  }')"
```

</CodeGroupItem>
</CodeGroup>

This example requires [jq](https://jqlang.org/) to encode the password safely as JSON. The API returns HTTP `201` and the new member. No invitation needs to be accepted before the managed user can sign in.

Use [Update a member](/api/members/update/) to change a managed user's `user.nickname` or `user.password`. These fields are not available for invited users. Setting a new password also enables the managed user's account.

## Remove access

**Removing a managed user from their last merchant account also deletes their login and ends their sessions.** Check which type of user you are removing before proceeding.

1. Use [Get a member](/api/members/get/) to confirm you have the correct person and account.
2. Call [Delete a member](/api/members/delete/) with the merchant code and the member's `id`.
3. Confirm that the member no longer appears in [List members](/api/members/list/).

The delete request returns HTTP `200` with an empty body. For an invited user, removal affects access to this merchant account; it does not remove their access to other merchant accounts.

Some members, including the account owner and Admin members, are protected from removal through this endpoint. The Members API also does not support removing service accounts.

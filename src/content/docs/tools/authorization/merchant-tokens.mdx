Merchant tokens give your application short-lived access to a specific SumUp merchant account for selected actions. Users sign in through your application's own authentication. Your backend checks their access, creates a token, and returns it to your app.

Each token is limited to one merchant account and the actions you request. It cannot grant more permissions than the identity that creates it. Keep your backend credentials on your server and give your app only the merchant token.

## Current support

Currently, the only supported action is `checkout`, for accepting in-person payments with a SumUp SDK that supports merchant tokens. The examples in this guide use that action.

Use merchant tokens only with integrations that explicitly document support for them. Available actions and integration support determine what a token can be used for.

## Before you begin

You need:

- A SumUp merchant account and its merchant code.
- Backend credentials with access to that account: an [API key](/tools/authorization/api-keys/) for an account you control, or an [OAuth access token](/tools/authorization/oauth/) for a merchant who has authorized your integration. The authenticated identity needs the `tokens.create` permission for the account.
- A way to authenticate users in your application and check which actions they can perform for each merchant account.
- A SumUp SDK version that explicitly supports merchant tokens. Check your SDK's authentication documentation before integrating; an SDK method that accepts OAuth access tokens does not by itself confirm merchant-token support.

Keep your API key or OAuth credentials on your backend. Only return the merchant token to the authorized app.

## How the token reaches your app

1. The user signs in to your application.
2. Your app requests a merchant token from your backend.
3. Your backend verifies the user's session and checks that they can perform the requested actions for the selected merchant account.
4. Your backend requests a token from SumUp for that account and the allowed actions. In the example below, the action is `checkout`.
5. Your backend returns the token to your app over HTTPS. Your app passes its `access_token` to the integration using its documented merchant-token authentication flow.

The user signs in to your application; your backend's credentials authorize the request to SumUp. For integrations serving other merchants, use OAuth to obtain their authorization before creating merchant tokens for their accounts.

## Create a token on your backend

Call `POST https://api.sumup.com/v0.1/merchants/{merchant_code}/tokens` with `actions` set to `["checkout"]`.

For this backend request, set `SUMUP_ACCESS_TOKEN` in your server environment to your API key or OAuth access token. Set `SUMUP_MERCHANT_CODE` to the account the token should grant access to. Install your chosen [server SDK](/tools/sdks/) before using its example. The Go SDK reads its credential from `SUMUP_API_KEY`; set that variable to your backend credential instead, and pass the authorized merchant code to `createMerchantToken`.

Run these examples only on your backend, after checking the user's access to the merchant account. The cURL command prints the secret token; keep its output out of logs.

A successful request returns HTTP `200` with a response like this. `MERCHANT_TOKEN` is a placeholder for the secret value:

```json
{
  "access_token": "MERCHANT_TOKEN",
  "token_type": "Bearer",
  "expires_in": 899
}
```

| Field          | Meaning                                                                                                             |
| -------------- | ------------------------------------------------------------------------------------------------------------------- |
| `access_token` | The secret value to pass to the integration. Treat it as an opaque string; do not parse it or depend on its format. |
| `token_type`   | Always `Bearer`.                                                                                                    |
| `expires_in`   | The remaining token lifetime in seconds when SumUp creates the response.                                            |

The examples make the SumUp request; your application's endpoint must enforce user access before running them:

- Verify the user's session on every token request.
- Resolve the merchant account from your own records, or check a requested merchant code against the user's allowed accounts. A merchant code supplied by the app is not proof of access.
- Check that the user can perform every requested action. For `checkout`, check that they can accept payments, not just view the account. Reject unauthorized requests before calling SumUp.
- Return the token only to that user over HTTPS, with `Cache-Control: no-store`. Keep credentials and tokens out of URLs, logs, analytics, and source code.

Keep the requested actions under backend control and request only those needed for the task. This payment example requests `["checkout"]`.

## Use and replace the token

Pass `access_token` to the integration's documented merchant-token authentication flow. For the `checkout` example, follow the supported SDK's reader setup and checkout instructions to accept a payment.

Tokens expire 15 minutes after creation. Use `expires_in` to track the remaining lifetime. When a new token is needed, request one through your backend and repeat the user and merchant access checks.

When a user signs out or switches merchant accounts, stop reusing the previous account's token and follow the integration's logout or account-switching instructions. Request a token for the newly selected account only after checking access again.

## Troubleshoot token creation

| HTTP status | What to check                                                                                                                |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `400`       | Send a JSON body with a non-empty `actions` array. Use only `checkout`, once. Unsupported or duplicate actions are rejected. |
| `401`       | Check the backend's API key or OAuth access token. Missing, invalid, or expired credentials cannot create a merchant token.  |
| `403`       | Check that the authenticated identity can create tokens for the merchant account in the request path.                        |

A successful token response confirms token creation. To verify the complete integration, authenticate a supported SDK with the returned token and follow the [in-person payment testing guide](/terminal-payments/testing/).
